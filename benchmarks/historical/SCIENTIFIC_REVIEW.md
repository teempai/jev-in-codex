# Scientific review of the broad sweep

## What was measured

The primary comparison is an explicit Jev-plugin workflow versus plain Codex on identical decision tasks. Both conditions use gpt-6-astra, medium reasoning, the same files, complete answer requirements, ordinary shell tools and clean ephemeral sessions. End-to-end elapsed time includes tool work and recovery. Codex total input, cached input, uncached input and output are separate from Jev provider usage. The actual packaged MCP server is loaded from its manifest; this is controlled CLI execution, not a test of desktop plugin discovery or automatic adoption.

Twenty distinct decision policies have working PoCs. Their common Choice engine is intentional; twenty policies do not imply twenty different architectures. The records exercise coding and general-work classification, not completion of twenty full real-world projects.

## Attribution

No local classifier supplies Jev labels. Each successful intervention must have provider-call evidence, validated provider decisions and complete final output. Plain Codex can use ordinary code to serialize its own decisions. Batching, serialization and uncertainty selection are parts of the integration: an end-to-end win would establish value for that combined workflow. It would not by itself show Jev beats another classifier in the same interface. A matched substitute-classifier control is needed for that stronger claim.

Actual-use failures and fallbacks remain in the record. Optional-use pilot nonadoption is retained separately from the explicit-use screen. The artifact-development round was blocked by its MCP approval configuration and made zero provider calls; it cannot establish model effectiveness. The corrected artifact-approved round changes only that one per-tool setting, with a successful Codex-level diagnostic first.

## Limitations that constrain conclusions

- The first screen has 160 unique authored records, eight per policy. Two technical repetitions do not double the independent sample size. The 32-record artifact development comparison has 64 new authored records across two cases. The larger feedback case adds another 64 unique authored messages and reuses them for a disclosed concurrency-tuning round.
- Reference labels were authored with the fixtures and reviewed against explicit policies by the same agent. They are not independent expert annotations. One overlapping label in the first screen is disclosed, with both frozen primary and symmetric exclusion analyses.
- These synthetic, mostly short records are easier and cleaner than real repository diffs, support queues or document collections. Their near-perfect Codex accuracy creates a ceiling for detecting precision improvements.
- The experimenter can see answer keys; benchmark Codex sessions are instructed to use only task files, and command traces are inspected for compliance. Keys are outside the supplied task and plugin roots. This is a controlled harness boundary, not a claim of adversarial isolation.
- Case selection and the 0.8 review threshold are development choices. Confidence is uncalibrated. Raw Jev errors, reviewed records and high-confidence escaped errors must all be reported alongside final accuracy.
- Fixed alternating execution order mitigates but does not eliminate load, startup and cache effects. Two repeats support descriptive ratios, not statistical significance or deployment guarantees.
- Total input savings are not monetary or subscription-quota savings. Provider usage, cached input and output may change differently; no verified invoice model is available here.
- A failed small-batch screen does not prove that larger workloads cannot benefit. Conversely, a selected larger-batch win does not overturn the reported small-batch losses or establish all twenty use cases are useful.

## Decision rule

Retain every scheduled result. Use the prospectively frozen development gate: all intervention outputs correct, actual Jev use, and at least 20% less paired geometric mean total Codex input or elapsed time with the other no more than 10% worse. Inspect class metrics, omissions, raw errors and commands before interpreting a pass. A pass identifies a candidate for new representative held-out evaluation; it is not a production recommendation. A failure remains a useful negative finding and must not be relabelled as a Jev gain.

No global instructions, external application actions or publication are part of these experiments.
